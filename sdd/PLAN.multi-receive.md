# Plan: Multi-Channel Receive

## Problem

A `session_token` is scoped to exactly one `(room, member)` pair, each with its own private `Inbox`. An agent that belongs to N rooms therefore holds N distinct session tokens and must call `receive` once per token. Because an MCP host serializes tool calls within one session, a single agent process cannot issue N concurrent `receive` calls — it can only poll its rooms one at a time. A message that lands in room B's inbox while the agent is parked in a `receive` on room A's inbox sits unseen for up to that call's entire `timeout_secs`, even though the agent is otherwise idle and available.

This caps ToasterTalk MCP at effectively one live room per agent identity for anything latency-sensitive; multi-room coordination degrades to slow round-robin polling, which cuts against the project's "no busy-waiting, no deadlocks" design goal.

### Root cause

`receive` blocks by calling `park_on_inbox` on exactly one `Arc<Inbox>`. That helper claims the inbox's single preemptible receive slot (a generation counter) before parking on its `Notify`. The single-slot design is a hard invariant, not an incidental limitation: `Notify::notify_one()` wakes one arbitrary waiter, so any inbox with more than one live waiter risks message theft by an orphaned one (ANTI-PATTERNS #8, the `surfing` deadlock). `park_on_inbox` is deliberately the *only* place any code is allowed to block-and-drain an inbox — both `receive` and the send-with-reply reply-wait funnel through it — precisely to keep that invariant structural rather than conventional. There is currently no primitive for waiting on more than one inbox at once.

There's a second, deeper root cause underneath that one: `session_token` itself is scoped to one room (`AppState.sessions: HashMap<SessionToken, (RoomToken, MemberName)>`). Even a `receive`-only fix would leave the server modeling "session" as "one room connection" rather than "one agent" — the approach below addresses both at once, because the second fix is what makes the first one simple instead of hard.

## Previously attempted

Not previously attempted — this is a new design question, not a revisited one. It is adjacent to but distinct from `sdd/PLAN.broadcast.md`: that plan is fan-**out** (one sender reaching many recipients in one room); this is fan-**in** (one recipient listening across many rooms it already belongs to). No naming or mechanism conflict, but both eventually revise the same baseline assumption — that `receive` is strictly single-channel — baked into `PRODUCT.md`'s vocabulary, so keep terminology consistent if both are ever implemented.

## Possible approaches

### 1. Extend `receive` to accept multiple session tokens

Change `receive`'s `session_token: string` field to `session_tokens: string[]` (or add a second, mutually-exclusive field), block until any one of the corresponding inboxes has a message, and tag each returned message with which room/session it came from.

**Pros**: One tool, no new concept for agents to learn; works within today's one-session-per-room model with no other changes.
**Cons**: Breaking change to `receive`'s request and response schema. Forces the riskiest part of this work — generalizing `park_on_inbox` from one inbox to N, and deciding whole-call-vs-partial preemption across them — directly into the most heavily exercised and hardened code path in the server. Every agent still needs to collect and pass N tokens on every call.

### 2. Add a new tool (e.g. `receive_any`) alongside the existing `receive`

Leave `receive` exactly as it is; add a second tool that takes `session_tokens: string[]` and returns messages tagged with their originating room/session.

**Pros**: No breaking change to `receive`'s existing contract.
**Cons**: A new tool is not free — it's permanent surface area every future agent has to be told about and every future change has to keep in sync with `receive`, on top of still needing the same N-inbox `park_on_inbox` generalization as approach 1. Rejected: a parameter on the existing tool (approach 3) gets the same result without the ongoing cost of a second tool.

### 3. One session token per agent, one shared inbox, optional `room` filter on `receive` (chosen)

Stop scoping `session_token` to a room. Split `connect` (mints a fresh, roomless session token — identity only, and nothing else) from a new `join` (attaches a room membership — room or seat token plus a member name — to an existing session token, hard-erroring if none is supplied) — so one agent, however many rooms it belongs to, holds exactly one token and one inbox, and every room membership it ever holds, including its very first, is created the same way: through `join`. `connect` never sees a room/seat credential or a member name at all, so there is no first-room special case to fall into and no way to silently split one's own identity by omitting a token on a later call. `receive` gains one new optional field, `room`: omitted (the default) blocks until a message arrives from *any* of the agent's rooms; supplied, it blocks (and drains) only messages from that specific room, leaving messages from other rooms queued for a later call. Every delivered message carries a `room` tag so the agent always knows where it came from. `send` gains a required room designator, since recipient `member_name` alone no longer disambiguates which room's namespace to search once one agent's shared inbox spans several. Send-with-reply's reply-wait reuses this same room-filtered wait internally — it needs the identical behavior (accept only a reply from the room the message was sent to), so it becomes a caller of the same primitive rather than a second bespoke one.

**Pros**: `park_on_inbox`'s single-inbox, single-preemptible-slot machinery is untouched at the concurrency level — there is still exactly one inbox and one slot per session. `receive` needs no new tool, only an optional filter field, and that same field does double duty for send-with-reply's mandatory room-scoped wait. `connect` does gain a sibling (`join`), but for a different reason than approach 2's rejected `receive_any`: `receive_any` would have existed purely to avoid touching `receive`'s contract, whereas `join` exists because a single overloaded field on `connect` cannot safely tell "first connect" apart from "attach to an existing identity" — an agent that omits the token on what should be a `join` call would otherwise get a second, silently split identity instead of a clear error. Making `connect` take *no* room/seat credential at all (rather than special-casing the first room, as first sketched here) turned out to be strictly simpler once rubric review reached it (see Technical details, below) — one tool with one job each, no branch in `connect` on credential type.
**Cons**: Requires the wider identity-model change as a foundation — a `room` parameter on `receive` has nothing to filter across until inboxes are shared per agent rather than per room-membership. Touches `connect`/`join`'s contract, `send`'s contract, and every eviction path, not just `receive` (see Technical details). `session_token` itself must now be handled with the same care as a persisted credential (see Decided, below) — an obligation that didn't exist when it was single-room and low-stakes to leak.

## Recommendation

Approach 3. The instinct behind approaches 1 and 2 — "receive needs to cover N rooms" — is right, but both solve it by making the *waiting* primitive more complex (N inboxes, N slots, whole-call-vs-partial preemption). Approach 3 solves it by making the *identity* model match what it should have been from the start: one session per agent, not one per room connection. Once that's true, `receive` barely changes — it still blocks on exactly one inbox, exactly one slot, no new preemption questions — and the only genuinely new piece of logic (a filtered drain that satisfies a wait on a subset of queued messages while leaving the rest queued) is small enough to share between `receive`'s optional room filter and send-with-reply's mandatory one, instead of building a parallel N-inbox mechanism, or leaving `connect` to silently guess intent from an optional field.

## Technical details preserved

### Data model
- `AppState.sessions` becomes `SessionToken → HashSet<(RoomToken, MemberName)>` instead of a single tuple. Every invariant check in `diagnostic_snapshot` (`state.rs:679`, `:735`, `:813`) that currently asserts a session resolves to exactly one `(room, member)` needs rewriting for "is this pair a member of the session's set," not equality.
- `MemberState` stays one entry per room membership (it still owns room-scoped `last_seen`, `auth`, `registered_at`), but its `inbox: Arc<Inbox>` is now the *same* `Arc` shared across every room-membership entry that belongs to one session, rather than a fresh `Inbox` per `connect`.

### `connect` (mint-only) and `join` (attach-only) — split into two tools
Closes the omitted-token gap directly: there is no longer a field whose absence is ambiguous between "this is genuinely my first connect" and "I forgot to pass my existing token." This section originally sketched `connect` as still taking a room/seat credential for an agent's *first* room, with `join` reserved for every room after that — rubric review (see `TDD.md` 1a/1b) simplified this further: `connect` takes **no room/seat credential and no member name at all**, ever. Every room membership an agent ever holds, first included, is created identically through `join`. This costs nothing extra — still just one additional tool overall (see Approach 3 Pros) — and removes a branch `connect` would otherwise have needed on credential type.

- **`connect`**: takes at most one optional input, `old_session_token`. No `old_session_token`: mints a fresh, roomless session token; nothing to register, nothing to evict. `old_session_token` supplied and names a still-valid prior session: invalidates that session token immediately and mints a fresh, roomless token in its place.
  - **Room/inbox carryover — deliberately dropped.** An earlier version of this section had `old_session_token` transfer the prior session's room memberships and queued inbox automatically. Revised after rubric review flagged the security consequence: since `connect` takes no room/seat credential to check, a bearer-only `old_session_token` presentation would be *sufficient by itself* to mint a replacement session inheriting every room the original belonged to — no proof of any room/seat credential required at all. That is strictly worse than the accepted skeleton-key risk documented below (which still requires the attacker to hold *some* legitimate credential for whatever room they reach). Decided instead: rotating via `old_session_token` invalidates the old session and everything under it — every one of its room memberships is evicted, not merely unlinked — and recovering access to any room afterward always goes back through `join`, using the room/seat token the agent still holds. Recovery becomes two-step (`connect`, then `join` per room) instead of one, but every step still demands proof of the credential it grants. This is the same recovery shape a post-restart reconnect already needs (see `1a.2`), so the two cases are now one mechanism instead of two.
- **`join`**: requires `session_token` — missing or unrecognized is a hard `InvalidSessionToken`, never a silent mint. Takes a room or seat token plus a member name, and attaches that room membership to the caller's existing session, sharing its inbox. This is now the *only* path by which any room membership is ever created. Preserves today's existing (and deliberate) asymmetry between the room-token and seat-token paths (`handle_connect` vs `handle_connect_seat`) as two branches inside `join`, rather than flattening it:
  - **Room token**: if the desired member name is already held by a different session, reject with `MemberNameTaken`. `join` never supersedes a room-token holder for a different session — there is no `old_session_token` escape hatch on `join` at all; that concept now lives solely on `connect`, and (per above) no longer carries room state.
  - **Seat token**: if the seat's `(room, member)` already has an active registration under *any* session — including one otherwise unrelated to the caller — unconditionally evict it as `Superseded` and register the new one, exactly as today's `handle_connect_seat`, just invoked through `join`. The eviction is per-membership (see Eviction, below), so it removes only that one room-membership from the superseded session, never that session's other rooms.
- **Rejoining a room the caller's own session already belongs to** (previously an open edge case, now settled): reject as redundant with a descriptive error (TDD `1b.7`) — not treated as a silent no-op.

### `send` contract
- Gains a required room designator (`room_name`, consistent with the existing `members` tool's own `room_name` field) since recipient `member_name` alone no longer disambiguates which room's namespace to look up.
- Send-with-reply's reply-wait currently drains and accepts *whatever arrives next* in the sender's own inbox (`wait_for_messages`, `send.rs:254`) — it doesn't even filter by sender today, only by "which inbox." It becomes the mandatory-filter caller of the same room-filtered wait `receive`'s optional `room` field uses: on wakeup, only a message tagged with the target room satisfies the wait; anything else that arrived in the same window stays queued for the agent's next `receive` rather than being swallowed by the reply-wait's drain.

### `receive`'s new `room` field and the drain it needs
- `room` omitted: block until any queued message is present, drain everything currently valid, same as today's `receive` except each returned message now carries its `room`.
- `room` supplied: block until a message tagged with that room is present, drain only messages matching it, leave the rest in the queue.
- This is a genuinely new primitive — today's `wait_drain_until`/`drain_valid` drain unconditionally. It needs a filter predicate threaded through the drain step. It is *not* a new preemption model: still one inbox, one slot, one live waiter — a later `receive` (filtered or not) or send-with-reply from the same session preempts whatever was previously parked on that shared inbox exactly as the single-room model already behaves today. The N-inbox "whole-call vs. partial preemption" question the earlier approaches raised does not arise here.

### Eviction — currently all-or-nothing per session; must become per-room-membership
- `evict_one` (`state.rs:471`) unconditionally does `sessions.remove(session_token)` and `inbox.close()`. Every eviction path funnels through it: room expiry, idle-TTL sweep, `kckm`/`kckall`, seat-supersede (now triggered exclusively by `join`, since `connect` no longer takes a seat credential — see above). Under the shared-inbox model, evicting a member from one expired/kicked room must remove only that room's membership entry — the session and its shared inbox may only be torn down once the *last* room-membership is gone. TDD `10.21`/`10.22` are the behavioral pin for this.
- `connect`'s `old_session_token` path is the one place a session *is* meant to be torn down wholesale (see the connect/join section above): invalidating an old session must remove *every* room-membership entry tied to it, not just the token-to-session mapping — an orphaned `MemberState` left behind after the session map entry is gone would violate the same invariant `13.7`'s diagnostics check for. This replaces the old bug that used to live in `handle_connect`'s reconnect path (`connect.rs:90`, `sessions.remove(stored_tok)` with no accompanying per-room cleanup) — moot as originally described, since `connect` no longer reconnects to a *specific* room at all, but the underlying "don't leave a dangling per-room entry behind" obligation still applies, now to the whole-session case.
- Stale-session cleanup after an agent crash/restart is accepted as partial, not solved: since neither a post-restart `connect` nor an explicit-rotation `connect` recovers any room membership (see above), an agent that only re-`join`s room A leaves whatever memberships it had in rooms B and C to decay independently via their own idle-TTL/room-expiry sweep, not as a side effect of the A rejoin.
- **In-flight blocking waits and partial eviction** (settled during implementation review, not originally scoped here): the pre-existing rubric (now `10.10`) that a blocking `receive`/reply-wait is aborted "when that member is evicted by any path" was written under the single-room model, where any eviction was necessarily whole-session. Now that eviction can be partial (one room membership evicted while others survive), that guarantee is scoped to whole-session teardown only — a `10.10b` was added to make this explicit: an eviction that empties one room membership but leaves the session's shared inbox backing at least one other membership does **not** abort an in-flight wait parked on that shared inbox; the wait keeps running until satisfied, preempted, or its own timeout. Implemented and tested (`state.rs`'s `evict_one_room_does_not_abort_receive_parked_on_surviving_room`); verified live over the real transport (`MANUAL-TEST.md` MT-9).

### ISS-001 interaction (revised from the original concern)
An earlier version of this plan (an N-inbox `receive`) would have *multiplied* the unbounded-batch exposure — up to N inboxes' worth in one call. A shared single inbox does the opposite: there's still exactly one `max_inbox_messages` budget, just now shared across every room the agent has joined. That trades one problem for another worth flagging explicitly — a chatty room A can fill the shared inbox and cause `InboxFull` rejections for messages from an unrelated room B (a cross-room noisy-neighbor effect that doesn't exist today, since each room currently gets its own independent budget). Note this as a new consideration for `ISSUES.md`'s batch-size entry once this ships, distinct from the multiplication concern it originally would have raised.

### Session resolution API
`AppState::resolve_session` (`state.rs:640`) and `AppState::touch_last_seen` (`state.rs:657`, called from `send.rs:203` and `receive.rs:169`) both assume a token resolves to exactly one `(room, member)`. Both need a room parameter so `touch_last_seen` stamps only the membership actually involved in a given call — done carelessly, it would either touch an arbitrary membership or touch all of them, defeating the already-decided per-room idle granularity.

### `members` tool
`tools/roster.rs`'s `handle_members` currently rejects with `NotConnectedToRoom` on an equality check (`actual_room_name != room_name`) against the single resolved room. Becomes a set-membership check once a session can belong to more than one room.

### Diagnostic dump rendering
The CLI `dump` (`mgmt.rs`) currently renders one `InboxSnapshot` per room-membership row. Once the inbox `Arc` is shared, every room row for one session would show identical, duplicated inbox contents — including messages destined for other rooms — repeated under each room block. Needs to render the inbox once per session (grouped), with each room row showing only its own membership metadata (`last_seen`, `auth`, `idle_countdown`).

### ISS-008 / ISS-010 — shape and severity unchanged
ISS-008's TOCTOU window now belongs entirely to `join` (the only tool that ever registers a room membership) rather than `connect`, and recurs once per room a session joins instead of once per session — still negligible, still self-healing, still requires a pre-existing valid credential to enter. ISS-010 gets a small incidental improvement once eviction is per-membership: a seat fight over one room's membership no longer collaterally evicts the victim's other live room memberships under the same session.

### Docs inventory (mechanical, for implementation time)
`SCHEMA.md`: `connect`'s new minimal contract (`old_session_token` only, no room/seat credential, no member name), `join`'s new contract (`session_token` + room/seat token + member name), `send`'s new room designator, `receive`'s new `room` field, the message object's new `room` field, `members`' room-scope wording, and `session_token`'s elevated sensitivity (see Decided, below). `TDD.md` rubrics already drafted and finalized for this plan: `1a.1`–`1a.4` (connect), `1b.1`–`1b.7` (join), `2.4`–`2.6` (send room designator/validation), `3.8`–`3.10` (receive room filter, tagging), `4.3` (reply-wait room filter), `5.3` (members set-membership), `10.21`–`10.22` (per-room eviction isolation), `10.10`/`10.10b` (in-flight wait vs. whole-session-only abort), `13.11` (diagnostics grouping) — plus a note on `13.3` that inbox Arc strong-count will read identically across a session's room rows once shared. `PRODUCT.md`: the "Vocabulary" open question's two concrete locations.

### Decided
- **Identity consistency across rooms**: member names can differ per room — a session is not required to present the same name everywhere it connects. A delivered message's `from` is always the room-scoped member name, and since every message also carries its `room` tag, a recipient always has enough context to reply into the right room even when the sender uses a different name in other rooms.
- **`last_seen`/idle-TTL granularity**: stays per room-membership, not promoted to the session as a whole — an idle room gets reaped even while the agent is actively working in another.
- **Auth-method mixing across a session's rooms**: confirmed no gap. `MemberState.auth` is already recorded per room-membership, not session-wide, so one session can hold a `RoomToken` membership in one room and a `Seat` membership in another with no new modeling — idle-TTL exemption already keys off the per-membership field, consistent with the per-room idle granularity above.
- **Vocabulary**: a session is the shared, multi-room identity bound to one `session_token`. What a room-token or seat-token grants within a single room is "room membership" (or "active room membership") — distinct from the session itself, which can span several. `PRODUCT.md`'s definitions need updating to this effect.
- **Client-side connect sequencing**: resolved by the `connect`/`join` split above — `connect` once (roomless), then `join` for *every* room, first included, never just "every room after." The split makes the sequence self-documenting instead of relying on an agent correctly remembering to pass (or not pass) an optional field.
- **Session-token leak blast radius (skeleton-key risk) — partially closed, partially accepted**: two distinct leak paths were considered, with different outcomes.
  - **Via `join` (accepted, unchanged from the original analysis)**: `join` authenticates the room being joined (via its room/seat token) but doesn't additionally prove the caller has any right to the `session_token` it supplies beyond holding the value. A leaked session token, combined with an attacker's own unrelated legitimate room/seat credential, lets the attacker attach to the victim's session and read its traffic across every room that session belongs to — a strictly larger blast radius than today's per-room session tokens. Decided: no added binding mechanism on `join`; instead `session_token` must be handled with credential-grade care for however long it lives. To be precise about what is and isn't changing: its *lifecycle* stays exactly as ephemeral as today — minted once per connect episode, reused across that session's many `send`/`receive`/`join` calls (never per-call), invalidated on disconnect/reconnect/eviction. What changes is the *consequence of a leak during that unchanged lifetime*: today a captured token exposes one room for its short life; here it exposes every room the session belongs to, for the same short life. Short-lived was never the same thing as safe-to-expose, and this design leans harder on that distinction than the single-room one did. Implementation must carry this through: `SCHEMA.md`'s description of `session_token` needs to say so explicitly, and agent-facing instructions (`README.md`, `AGENTS.md`, the MCP server's own onboarding text) must tell agents to handle it like a credential — never log it in full, never paste it insecurely — while it's live, not because it now lives longer. This also amplifies ISS-002 (plaintext transport): a captured session token is now a bigger prize. Add a note to that entry when this ships.
  - **Via `connect`'s `old_session_token` (closed, caught during rubric review, not part of the original analysis)**: an earlier revision of this plan had `old_session_token` transfer the prior session's rooms and inbox automatically on rotation. That would have meant a bearer-only presentation of a leaked `session_token` — with **no room/seat credential at all** — was sufficient to mint a full replacement identity inheriting every room the victim belonged to. That is a strictly worse skeleton key than the `join` case above, which at least requires the attacker to hold some legitimate credential for whatever room they reach. Closed by decision: `connect`'s `old_session_token` path never carries over room memberships or inbox contents — it only rotates the token value and tears down the old session's room memberships wholesale. See the `connect`/`join` technical section above and TDD `1a.4`.
- **Rejoining an already-held room membership**: settled (was an open edge case) — `join` rejects it as redundant with a descriptive error rather than treating it as a no-op (TDD `1b.7`).
- **In-flight wait vs. partial eviction**: settled — a blocking `receive` or send-with-reply parked on a session's shared inbox is aborted only when the triggering eviction empties that session's *last* room membership (whole-session teardown, `10.10`). An eviction that removes one room membership while at least one other survives leaves any in-flight wait on the shared inbox running untouched (`10.10b`) — it keeps waiting until satisfied by the surviving room's traffic, preempted by a newer call, or its own timeout elapses. Chosen over aborting on any eviction (which would spuriously interrupt an agent still legitimately listening for its other rooms) for simplicity and because it matches how the shared inbox already behaves for every other purpose — one wait, one slot, scoped to the session as a whole, not to any single room membership.

### Why keep a session token at all (settled, not open)
Room/seat tokens are deterministic and persistent — the same value every time — which is exactly what makes them unsuitable as a live-connection identity: two calls bearing the same seat token are indistinguishable whether they're a legitimate reconnect or an unrelated process holding the same credential. A session token's value is that it's ephemeral and changes across reconnects, which is what makes `Superseded` detection, single-connection revocation (`kckm`/idle-TTL/room-expiry) independent of the persisted credential, and safe log/dump redaction possible at all. This plan changes what a session token *scopes to* (one agent instead of one room), and now also what it's worth to an attacker (see the skeleton-key decision, above) — but doesn't remove the need for it.
